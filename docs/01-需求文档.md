# Taiji · 基于 LLM 的操作系统（Go 原生 Agent Harness）需求文档

> 项目名称：**taiji**
> 版本：v1.4.2
> 日期：2026-09-24
> **产品定位**：**基于 LLM 的操作系统**——内核是 Agent Loop，系统调用是工具（MCP），用户是 Principal，资源是工作区。权限模型必须按操作系统标准：默认拒绝 / 身份不可伪造 / 权限判定与执行分离 / 一切拒绝留痕
> **实现形态**：Go 原生 agent harness——以 trpc-agent-go 的工程形态为基础，借鉴 dsh 的会话日志/事件溯源与 capability seam 理念，引入 Tianshu-harness 的认知治理层，**并以 happyclaw 的 IM 渠道抽象实现渠道接入与权限管控（飞书优先）**
> 参照系：**dsh**（`deepseek-harness`）、**happyclaw**、**Tianshu-harness**、**trpc-agent-go** 四项目源码直读
> 次要对照：**WeKnora**（仅渠道层交叉验证，理由见 1.2.1）

> **v1.4.2 修订（2026-09-24）**：定位表述由单一的「生产级 Go agent harness」改为**两层表述**——

## 1. 背景与问题定义

### 1.1 四个参照系

本需求基于对四个核心开源项目的源码调研，**四者解决的是正交问题**：

| 项目 | 语言 | 回答的问题 |
|---|---|---|
| **DeepSeek Harness (dsh)** | TypeScript | 系统如何**可替换**（一切皆插件） |
| **HappyClaw** | TypeScript | 工程如何**可靠**（多渠道路由、并发串行化、权限矩阵） |
| **Tianshu-harness** | TypeScript | 模型如何**可信**（认知治理、证据门禁） |
| **trpc-agent-go** | Go | Go 生态的**工程形态**（多租户、可观测、存储可插拔） |

> **关于 WeKnora**：调研期间也考察了 WeKnora（Go，`internal/im/`）的 IM 渠道层。它作为**次要对照**保留（其飞书验签、租户降权等实现与 HappyClaw 互证），但**不作为独立参照系**——因为 HappyClaw 在渠道抽象上更完整（8 渠道 + 12 层权限矩阵 + 话题路由），取 HappyClaw 的抽象即可覆盖 WeKnora 的贡献面。文档中保留的 WeKnora 引用均为**交叉验证用途**，不是设计来源。

**DeepSeek Harness (dsh)** —— TypeScript，基于 Cordis 插件内核。核心主张是"一切皆插件"：model adapter、tool registry、session log、agent loop 全部是可替换插件。其架构基石是三条：
- **可逆 effect**：任何注册（服务、事件监听、prompt 段、工具 schema）都通过 `ctx.effect()` 安装，卸载时逆序 unwind（`vendor/cordis/src/fiber.ts:418` 定义 `effect()`，`:675-676` 的 `_unload` 用 `_disposables.clear()` 拿到逆序数组并发拆卸）。
- **会话日志是唯一事实源**：`packages/core/agent-loop/src/invariant.ts:42` 用 `JSON.stringify(options.messages) !== JSON.stringify(session.deriveMessages())` 断言"发给模型的请求必须能从日志重建"，失败即报 `log-reconstruction desync`。
- **窄接口 + 声明合并**：`Agent` 稳定面只有 `{ readonly id: SessionId }`（`packages/core/agent/src/types.ts:14`），全部 live 能力通过 `declare module` 在 `runtime-types.ts` 合并补充。

**HappyClaw** —— TypeScript，自托管多用户 AI 智能体系统（8 个 IM 渠道）。它回答"**工程如何可靠**"，是四者中**唯一把渠道接入与并发调度做到生产级**的：
- **会话串行化**：`src/group-queue.ts:935-942` 的 `findActiveRunnerFor` 用**派生键**（非 JID）匹配，使同一工作区的多个会话共享串行化域；`hasCapacityFor`（`:944-952`）按执行模式分叉——进程内模式不设全局配额（避免 warm idle 会话阻塞无关会话），容器模式保留限额。
- **渠道抽象**：绑定模式（`single_context`/`thread_map`）× 路由模式（`single_session`/`thread_map`）两个正交维度（`src/types.ts:42-43`）；话题用**虚拟 JID** 表达（`src/channel-native-context.ts` 的 `buildNativeThreadRouteJid`），每个话题创建独立 agent。
- **触发门禁 fail-closed**：`src/feishu-mention-gate.ts` 的 `evaluateMentionGate`——`botOpenId` 未知时**拒绝**（源码注释记录了历史 fail-open bug：旧实现"安全降级=默认放行"导致 `require_mention` 静默失效）。
- **运行时控制值隔离**：`docs/RUNTIME-ARCHITECTURE.md:61` 依赖规则第 4 条——控制值来自**受信启动环境**，不来自工作区可控的环境文件；实现见 `src/runtime-config.ts:647, 2056, 2408`（三处保留键检查）+ `:1954`（值清洗）。
- **权限矩阵**：`docs/ACL-MATRIX.md` 12 层，核心原则是 **admin 不自动绕过工作区所有权**（类型层体现：`src/group-acl.ts` 的 `role` 参数被接收但函数体从不引用）。

**Tianshu-harness** —— TypeScript（v3.24.0），定位是"面向 Foundation Model Agent 的**认知运行时**（CVM）"。它回答"**模型如何可信**"——前两者解决"系统能不能跑"，Tianshu 解决"模型会不会跑偏"：
- **运行时 hook 管线**：5 阶段 `preTurn → afterPerception → postTool → postTurn → postSession`（`src/agent/runtime-hooks.ts:8`、`:234-238`），模块约 60+，按依赖与环境变量条件装配。
- **三道反锚点结构**：TaskContract（全局目标独立状态，`src/context/task-contract.ts:11`）、Evidence 门禁（`src/agent/delivery-gate-v2.ts:83` 的 GREEN/YELLOW/RED 三态 + `evidence-obligation.ts:11-15` 的义务状态机）、Convergence 检测（`src/agent/convergence-detector.ts:998`，7 信号按阶段加权）。
- **状态感知**：Sensorium 六维纯函数（`src/agent/sensorium.ts:321`，注释声明 `<1ms`，无 I/O 无 LLM）。
- **前缀缓存引擎**：冻结前缀 + 增量 appendix + 边界压缩，把缓存命中率做成架构级承诺（`src/prompt/engine.ts:155/157/168`）。
- **可逆性的分层答案**：编译期装配的 CVM 核心 hook **不可逆**（`runtime-hooks.ts:251` 只有单向 `register`，无 `unregister`/`clear`），而运行期的用户扩展 hook **可逆**（`src/hooks/registry.ts:19` 有 `unregister`、`:86` 有 `clear`）。

**trpc-agent-go** —— Go，腾讯开源的生产级 agent 框架。它回答"**Go 生态的工程形态**"——是四者中唯一用 Go 实现生产级 agent 的：
- **callback 式扩展**：`Plugin{ Name(); Register(r *Registry) }`（`plugin/manager.go:33-40`），Registry 暴露 9 个 hook 点（`BeforeAgent:71` / `AfterAgent:89` / `BeforeModel:107` / `AfterModel:125` / `BeforeTool:143` / `AfterTool:161` / `AfterToolMessages:180` / `OnEvent:191` / `AfterRun:202`）。
- **插件不能替换组件**：`agent/plugins.go:26-45` 的 `PluginManager` 接口只有 callbacks getter + `OnEvent` + `Close`，**没有任何组件 setter**。工具集的影响只能通过"改请求"（`plugin/toolsearch/plugin.go:518` 直接写 `args.Request.Tools[name]`）间接实现。
- **状态物化存储**：`Session.State` 是 `StateMap`（`session.go:67`），sqlite 后端在 `service_helper.go:301` 的 `addEvent` 里**同事务**写 state 列与 event 行；`grep Replay|Rebuild|reconstruct session/*.go` 无命中——**不存在从事件日志重建状态的机制**。
- **多租户键**：`{AppName, UserID, SessionID}` 三级（`session.go:1180`），`runner.Run(ctx, userID, sessionID, ...)` 直接接收（`runner.go:544-550`）。

### 1.2 核心问题

四个项目各自证明了架构的一个侧面，但**没有一个是完整的生产级 Go 方案**：

| 能力 | dsh | happyclaw | Tianshu-harness | trpc-agent-go |
|---|---|---|---|---|
| 可逆 effect（注册即可卸载） | ✅ 核心机制 | ⚠️ **分层**：核心不可逆，扩展可逆 | ⚠️ **分层**：CVM 核心不可逆，用户 hook 可逆 | ❌ 只有 callback 注册 |
| 组件替换（换 provider 即换产品） | ✅ `ctx.<key>` 换实现 | ❌ 无插件系统（不涉及） | ❌ 硬编码白名单（仅 3 项让位） | ⚠️ 构造期 `WithXxx` |
| agent loop 可替换 | ✅ `Agent` 接口窄到 `{id}` | ❌ loop 固定 | ❌ loop 固定 | ❌ loop 锁在 llmagent 内 |
| 日志派生状态（可从日志重建） | ✅ 运行时不变式断言 | ⚠️ 部分派生（`session-persist.ts:220` mergePending） | ⚠️ 部分派生 | ❌ state 物化，无重建 |
| 类型化事件总线 | ✅ declaration merging | ❌ 靠 TS 联合类型 + hook 阶段 | ❌ 靠 TS 联合类型 + hook 阶段 | ❌ 靠 `Response.Object` 字符串判别 |
| **会话串行化** | ❌ | ✅ **核心机制**（派生键 + 容量分叉） | ❌ | ❌ |
| **渠道接入与权限矩阵** | ❌ | ✅ **核心机制**（8 渠道 + 12 层） | ❌ | ❌ |
| **控制值隔离** | ❌ | ✅ **核心机制**（受信环境 + 3 处检查） | ❌ | ❌ |
| **目标不漂移（TaskContract）** | ❌ | ❌ | ✅ 核心机制 | ❌ |
| **完成有证据（Evidence Gate）** | ❌ | ❌ | ✅ 核心机制 | ❌ |
| **停滞能检测（Convergence）** | ❌ | ❌ | ✅ 核心机制 | ❌ |
| **前缀缓存优化** | ⚠️ 未强调 | ❌ | ✅ 架构级承诺 | ❌ |
| 生产级多租户 | ⚠️ profile 机制 | ✅ 工作区 ACL + 12 层矩阵 | ⚠️ 单机为主 | ✅ AppName/UserID/SessionID |
| 可观测性 | ⚠️ | ⚠️ | ⚠️ | ✅ OTel 集成完整 |

**本项目的核心问题**：在 Go 语言约束下，如何构建一个**基于 LLM 的操作系统**——它既是生产级 agent harness（实现形态），又具备操作系统的权限严谨性（产品定位）？

- 从 **dsh** 取：可逆 effect 语义、日志派生纪律、capability seam 三层结构
- 从 **happyclaw** 取：会话串行化、渠道抽象（绑定×路由双维度 + 话题虚拟 JID）、fail-closed 门禁、控制值隔离
- 从 **Tianshu-harness** 取：认知治理层（TaskContract / Evidence / Convergence）、Sensorium、前缀缓存
- 从 **trpc-agent-go** 取：Go 工程形态、多租户键、9 个 hook 点、可插拔存储、OTel 可观测

### 1.2.1 为什么是这四个（关于 WeKnora）

调研期间还查阅了 **WeKnora**（`E:\aiops\WeKnora`，`internal/im/`）的 IM 渠道层。**它不列入参照系**，理由：

| 维度 | happyclaw | WeKnora | 结论 |
|---|---|---|---|
| 会话模式 | 绑定模式 × 路由模式（**两个正交维度**） | `SessionMode` 二选一开关 | happyclaw 更完整 |
| 话题隔离 | 虚拟 JID + 独立 agent 实例 | `thread_id` 字段 | happyclaw 更完整 |
| 触发门禁 | audience × activation 正交 + fail-closed | 无 | happyclaw 独有 |
| Owner 模型 | 显式认领 + break-glass | 无 | happyclaw 独有 |
| IM 用户权限 | 12 层矩阵 + admin 不绕过 | 统一降级为 Viewer | 两者方向一致，happyclaw 更细 |

**WeKnora 的价值是交叉验证**，不是提供新设计：它的"验签+解密"、"IM 用户降权"、"渠道管理需 Admin"三条与 happyclaw 独立实现且方向一致——这**证明了这些不是 happyclaw 的特有选择，而是渠道接入的通用要求**。

因此本文档的参照系是**四个**（dsh / happyclaw / Tianshu-harness / trpc-agent-go）。WeKnora 的引用仅作为**对照证据**保留在 FR-10 与附录 A，不作为设计来源。

### 1.3 为什么不做完整复刻（A 档被否决的理由）

dsh 的若干核心机制**在 Go 中无法原样实现**，这不是工程投入问题，是语言边界：

- **声明合并（declaration merging）不存在于 Go**。dsh 靠它把"同一 context 上挂多种事件类型"做成类型安全的。Go 的等价物受限：泛型方法在 Go 1.27 已支持（实测 `func (b *Bus) Emit[E any](e E)` 可编译运行），但**泛型接口方法仍不合法**（实测报错 `interface method must have no type parameters`）。因此"一个接口暴露多种事件类型"无法原样建模。
- **运行时进程内插件加载**：Go 标准库 `plugin` 包官方文档明确 `A plugin is only initialized once, and cannot be closed`（无卸载），且**不支持 Windows**、race detector 支持差、工具链版本必须完全一致。

**结论**：B 档（Go 原生 harness）是工程上唯一务实的选择——**放弃"进程内动态加载任意插件"这一形态**（Go 无法卸载、不支持 Windows），改为**编译期装配 + 运行期可逆注册**。dsh 的"日志即真相"能力与 Tianshu 的"认知治理"能力则通过自建内核引入。

> **注意区分两件事**（此前表述混淆，此处澄清）：
> - **不可复刻的是「运行时加载新代码」**——Go 的 `plugin` 包限制。
> - **可复刻的是「注册/卸载已有能力」**——本设计采用 dsh 的可逆 effect 语义，在进程内实现（见 FR-2.0 分层模型）。
>
> 即：**扩展范式仍是 effect（可逆注册），只是不做运行时 dlopen**。

## 2. 目标与非目标

### 2.1 目标（Goals）

**G1. 生产级多租户 agent 运行时**
支持单进程内多应用（app）、多用户（user）、多会话（session）三级隔离，可水平扩展，具备完整的并发控制与优雅关闭。

**G2. 会话日志作为唯一事实源**
引入 dsh 的核心理念：模型可见的上下文必须能从 append-only 会话日志重建。与 trpc-agent-go 的差异点在于——**state 可选派生而非仅物化**，为审计、回放、调试、迁移提供基础。

**G3. 可逆的能力注册**
引入 dsh 的可逆 effect 语义到 Go：任何能力注册（工具、模型适配器、事件监听、prompt 段）都返回 disposer，卸载时逆序 unwind。这是对 trpc-agent-go "callback 注册无法卸载"的补强。

**G4. 能力 seam（三层结构）**
每个可替换能力遵循 dsh 的 Definition / Provider / Consumer 三层结构，使"换一个 provider 改变整个产品"成为可能（如把本地文件系统换成远程沙箱，Bash/PTY/LSP 跟着迁移）。

**G5. 完整的生产可观测性**
OpenTelemetry trace/metric 覆盖 agent 全生命周期，支持 Langfuse 等后端。

**G6. 扩展范式明确且一致**
新行为一律挂到已文档化的扩展点，不改核心 loop。这条是 dsh 的纪律，需在 Go 中以接口 + 注册表的形式落地。

**G7. 操作系统级权限严谨性（新增·v1.4.2）**
Taiji 的产品定位是**基于 LLM 的操作系统**，因此权限不是附加功能，而是内核职责。四条硬约束：

| 约束 | 含义 | 落点 |
|---|---|---|
| **默认拒绝** | 未显式授权的动作一律拒绝，不是「默认放行再收紧」 | FR-9、`authz/toolpolicy.go` |
| **身份不可伪造** | 主体从平台元数据实取，不信任调用方传入 | FR-10.2、`authz/principal.go` |
| **判定与执行分离** | 权限判定在插件层，执行在内核层，判定不内嵌于工具实现 | FR-4、`authz/permission_plugin.go` |
| **一切拒绝留痕** | 拒绝必须可审计——静默失效是最难排查的缺陷 | FR-10.9 |

**为什么单列此目标**：原表述把定位写成「生产级 Go agent harness」，只描述**实现形态**，
未表达**产品是什么**——导致权限需求缺少判断依据（为何必须 fail-closed？为何 admin 不绕过资源所有权？）。
「操作系统」这一类比直接推出上表四条：内核不信任用户态输入、系统调用逐次鉴权、
root 也不该无视文件属主。详见 `08-命令系统与RBAC需求文档.md` §1。

### 2.2 非目标（Non-Goals）

**N1. 不追求运行时热插拔（HMR）**。dsh 有 HMR（配置热重载），但 Go 无成熟进程内模块卸载机制。本项目的能力注册在**启动期与受控的配置变更期**完成，不做任意时刻的插件热替换。

**N2. 不追求 agent loop 的任意替换**。loop 保持固定（标准"调模型-跑工具-循环"），但**所有可插入点都做成扩展点**。dsh 自己也承认 loop 极少需要改（`packages/core/agent-loop/README` 原文："只有标准的『调用模型、运行工具、重复』生命周期无法满足需求时，才应选择自定义 Agent 实现"）。

**N3. 不做声明合并的类型安全事件总线**。Go 语言不支持，改用"每事件类型一个总线 + 代码生成/泛型函数"的绕行方案。

**N4. 不实现 WASM 插件沙箱**。作为未来演进方向记录，不在 v1 范围。

**N5. 不替代 trpc-agent-go 的全部生态**（如 A2A、AG-UI、MCP 集成等已有能力应复用而非重造）。

**N6. 「操作系统」是定位类比，不是实现目标（新增·v1.4.2）**。
「基于 LLM 的操作系统」表达的是**权限与抽象层次的设计标准**——内核/系统调用/主体/资源的分层，
以及由此推出的四条权限硬约束（G7）。它**不意味着**：
- 不做真实 OS 功能（进程调度、内存管理、文件系统驱动）；
- 不要求自研内核替代 trpc-agent-go（N5 已声明复用优先）；
- 不引入内核态/用户态的硬件级隔离（Go 进程内无法做到）。

> 划这条边界的理由：定位类比若不设边界，容易被读成「要重写一个操作系统」，
> 从而推出错误的优先级（如优先做资源隔离而非权限正确性）。
> 本项目的「操作系统」类比**只在权限模型这一层成立**。

## 3. 功能需求

### FR-1 会话与事件日志

**FR-1.1 append-only 会话日志**
- 每个 session 对应一份 append-only 的事件日志，事件一旦写入不可修改。
- 事件带单调递增的序列号（seq），保证顺序。
- 日志物理格式支持 JSONL（首期）与可插拔后端（SQLite、PostgreSQL 等）。

**FR-1.2 事件词汇表**
需要定义完整的事件类型集合，至少覆盖：
- 生命周期：`turn/start`、`turn/end`、`step/start`、`step/end`
- 消息：`user/message`、`assistant/message`、`system/message`
- 工具：`tool/call`、`tool/result`
- 请求：`request/header`、`request/context`
- 尝试：`assistant/attempt`（记录失败/重试/取消，不进入模型历史）

**FR-1.3 状态派生（核心需求）**
- 提供 `DeriveMessages(sessionID) []Message`，从日志投影出模型可见的消息历史。
- 提供**运行时不变式校验**：发往模型的请求必须与日志派生结果一致，不一致时 fail-loud（对齐 dsh 的 `invariant.ts:42` 语义）。
- 支持从日志**重建**会话状态（回放），用于调试、审计、迁移。

**FR-1.4 崩溃恢复**
- 进程崩溃后重启，能从日志恢复到最后一个完整事件边界。
- 未闭合的 turn（有 `turn/start` 无 `turn/end`）需要修复策略：写路径补 `turn/end`，冷读路径只在内存中平衡（对齐 dsh 的 `interruptedTurnClosers` 语义）。

**FR-1.5 日志格式版本与迁移**
- 日志格式带版本号（`SESSION_FORMAT_VERSION`）。
- 支持相邻版本迁移链（`vN -> vN+1`），迁移不得覆盖或删除已提交的代（generation）。
- 未知的未来版本必须拒绝加载（fail-closed），不静默降级。

### FR-2 能力注册与可逆 effect

**FR-2.0 可逆性的分层模型（定义）**

> **术语定义**：本设计中的"可逆"**不是一刀切**，而是按注册时机分两层。这是对 dsh 语义的**有意收窄**，理由见设计文档 4.4.1（Hook Pipeline 的分层可逆性）。

| 层次 | 注册时机 | 可逆性 | 用途 |
|---|---|---|---|
| **核心注册** | 编译期装配 | **不可逆** | 保证行为稳定与缓存前缀稳定 |
| **扩展注册** | 运行期 | **可逆**（返回 Disposer） | 保证隔离卸载与多租户灵活 |

- **核心注册**：`Register(hook)`——无返回值，不可卸载。装配在编译期决定，运行期只能**禁用**（`SetDisabled`）不能移除。
- **扩展注册**：`RegisterExtension(hook) Disposer`——返回 disposer，可逆。

**为什么分层**：若一切可逆，多租户的隔离卸载会破坏核心稳定性；若一切不可逆，扩展无法隔离。分层是两者兼得的答案（对齐 **Tianshu-harness** `runtime-hooks.ts:251` 核心不可逆 vs `hooks/registry.ts:86` 扩展可逆的实测差异）。

**FR-2.1 可逆注册（适用于扩展注册层）**
- **扩展注册**返回 `Disposer`（`func() error`）；**核心注册**不返回（见 FR-2.0）。
- 卸载时按注册的逆序执行 disposer（LIFO）。
- 卸载失败需聚合错误并报告，不静默吞掉。

**FR-2.2 作用域隔离**
- 支持根作用域与子作用域（per-agent / per-session）。
- 子作用域卸载时，其注册的能力被 unwind，父作用域不受影响。
- 子作用域能访问父作用域的服务，反之不能。

**FR-2.3 能力 seam（三层）**
- **Definition**：声明接口（如 `ctx.llm`、`ctx.tools`、`ctx.fs`）。
- **Provider**：实现接口并注册到 Definition。
- **Consumer**：通过接口使用能力，不 import 具体实现。
- 一个包可同时承担多个角色，但**单一角色不构成 seam**。

**FR-2.4 依赖声明与加载序**
- Provider 通过声明依赖表达加载顺序，而非手工编排启动序列。
- 依赖未就绪时，强依赖读取必须**显式报错**而非返回 nil/零值（对齐 dsh `reflect.ts:160` 的 `cannot get required service "..." in inactive context`）。
- 依赖换实现时，依赖方需被通知重新解析。

### FR-3 Agent Loop 与事件

**FR-3.1 标准 loop**
- 固定实现"组装 prompt → 调用模型 → 流式接收 → 执行工具 → 判断是否继续"的循环。
- turn/step 语义明确：step = 一次模型请求 + 它触发的工具调用；turn = 零或多个 step。

**FR-3.2 事件扩展点**
- 提供事件拦截点，支持 observe（观察）与 intercept（拦截）两种语义。
- **支持五种 dispatch 模式的定义**：`emit`（观察，无返回）、`waterfall`（环绕中间件，可短路）、`serial`（顺序，有返回）、`bail`（首个非空值即停）、`parallel`（并行扇出，无返回，等待全部完成）。
- **v1 实现其中四种**（`emit`/`waterfall`/`serial`/`bail`），`parallel` 推迟——理由见设计文档 4.2。
- **waterfall 语义**：监听器必须调用 `next()` 委派，不调用即短路（对齐 dsh `cordis-primer.md` 的 Waterfall Semantics）。

**FR-3.3 取消与中断**
- 支持取消正在进行的 turn，已流式交付给用户的文本必须保留。
- 支持多轮重试（retry），重试不重复 prompt 组装。

**FR-3.4 多 agent 协作**
- 支持子 agent 委派（subagent），带递归深度预算。
- 支持多 agent 编排（chain / parallel / cycle）。

### FR-3.5 认知治理层（FR-3 的扩展，新增·借鉴 Tianshu-harness）

> **来源**：本节来自对 Tianshu-harness v3.24.0（`E:\aiops\Tianshu-harness`）的源码调研。它与 dsh 解决**正交问题**——dsh 管"系统如何可替换"，Tianshu 管"模型如何可信"。生产级 harness 两者都需要。

**背景命题**：模型的能力上限 ≠ 运行行为。经指令与偏好对齐的 Transformer Agent 会呈现趋同的运行时退化（被质疑即投降、局部信息压过全局目标、长上下文被早期结论支配、反复调用同类工具却无推进）。Tianshu 将此命名为 **Cognitive Anchor Collapse**，并主张解法不是更好的 prompt（prompt 是信息不是状态），而是模型之外的**确定性监督层**。

**FR-3.5.1 任务契约（TaskContract）**
- 全局目标必须拥有**独立于对话历史的状态**，不能依赖"用户最近一句话"来定义任务。
- 契约字段至少含：objective、scope、constraints、success criteria、lifecycle status。
- 状态需**单调推进**，降级需显式授权（对齐 Tianshu `task-contract.ts:265-283` 只放行一条降级弧的设计）。
- 上下文压缩后，契约需以**权威块**形式重注入，并声明权威性（对齐 `renderTaskAnchor` 的 `authoritative="true"`）。
- 新输入必须与契约对照，不得自动等价于任务的最新定义。

**FR-3.5.2 证据门禁（Evidence Gate）**
- **完成声明必须带运行时证据**（测试结果、diff、验证命令），"模型说完成"不等于"运行时确认完成"。
- 门禁产出三态：GREEN（可交付）/ YELLOW（有外部阻塞但自有部分已验证，可带条件交付）/ RED（自有失败或未验证，禁止交付）。
- 证据义务是**状态机**而非散落检查：`satisfied` 是唯一终态，`blocked ≠ satisfied`（高风险义务不因受阻而被当作已关闭）。
- bugfix 类义务需先 RED（失败复现）后 GREEN。

**FR-3.5.3 收敛检测（Convergence）**
- 独立判断"认知轨迹是否还在推进"，不依赖模型自述。
- 检测信号至少覆盖：编辑比、目标新颖度、工具熵、错误惩罚、token 效率、振荡惩罚、文本重复。
- 判定需按**任务阶段**加权（探索/规划/执行/验证/交付阶段判据不同）。
- 需能识别 doom-loop（同类工具重复调用）与 tool storm。
- **护栏取向**：宁可漏报不可误熔断——熔断需多重确认（分数持续下降 + 此前已警告 + 无进度信号）。

**FR-3.5.4 状态感知（Sensorium）**
- 需有零 LLM 开销的运行时状态感知（纯函数计算，目标 <1ms）。
- 感知维度至少覆盖：推进动量、上下文压力、验证覆盖度、复杂度、新鲜度、稳定性。
- 每个维度需标注**是实测还是无数据回退**，使消费方能区分真实信号与空值。

### FR-6 多租户与隔离

**FR-6.0 核心概念定义**

> **术语定义**（此前三处正文使用但未定义，此处集中定义）：

**执行上下文（Execution Context）**
- 一次 run 的运行时身份与资源边界，随调用链传播。
- 至少携带：`{TenantKey, SessionID, RunID, Cancel Signal, ContextKind}`。
- **`ContextKind`** 区分执行来源，是权限判定的依据（见 FR-10 与附录 B.1）：

| ContextKind | 含义 | 写权限 |
|---|---|---|
| `interactive` | 顶层交互式会话 | 按 ACL |
| `scheduled` | 定时任务触发 | **只读** |
| `subagent` | 子 agent 委派 | **只读** |
| `channel` | IM 渠道消息 | **只读**（降级，见 FR-10.7） |

- **上下文丢失必须 fail-closed**：无 `ContextKind` 时拒绝写操作，不得默认为 `interactive`。

**工作区（Workspace）**
- **租户内的一级资源容器**，是文件、会话、渠道绑定、长期记忆的归属单位。
- 归属关系：一个工作区恰好属于一个用户；**一个会话恰好属于一个工作区**。
- 层级：`AppName → UserID → Workspace → Session`。
- **权限边界**：工作区所有权（owner）是资源级授权的依据，**admin 不自动绕过**。
- **串行化粒度**：同一工作区的多个会话共享串行化域（见 NFR-8.2）。

> **与 FR-6.1 三级键的关系**：三级键 `{AppName, UserID, SessionID}` 是**存储与隔离键**；工作区是**资源归属与授权单位**。
>
> **为什么工作区不提升为键的一级**：归属关系是 `Workspace : Session = 1 : N`（一个会话恰好属于一个工作区），所以工作区是**会话的属性**，不是与 SessionID 平行的维度。若提升为一级，键空间会包含 `{App, User, W1, S1}` 与 `{App, User, W2, S1}` 这类**非法组合**（同一 SessionID 归属两个工作区），需额外约束排除——用键空间换取了"字段在键里"的观感，代价是穿透存储层的大改（`TenantKey` 结构、`Runner.Run` 签名、所有后端 key 生成、所有 `checkSessionKey` 调用点）外加既有数据的迁移成本。**故保持三级键不变。**
>
> **工作区的载体**：工作区 ID **编码在会话标识中**，格式为 `{workspaceId}#{localSessionId}`（对齐 happyclaw `channel-address.ts:88` 的 `jid.split('#')[0]`）。这使 `DeriveKey(jid) string` 保持**纯字符串解析、零 IO、无 error 返回**——串行化器无需回查会话存储即可在热路径派生键。**注意**：不要实现为"运行期回查 Session 元数据字段"，那会在 run 启动前引入一次存储往返与竞态窗口，且与 `DeriveKey` 的纯函数签名不兼容。代价是会话标识的格式受约束（不能自由命名），这是与 happyclaw 一致的取舍。

**FR-6.1 三级隔离**
- 会话键为 `{AppName, UserID, SessionID}` 三元组。
- 用户级键为 `{AppName, UserID}`。
- 应用级隔离：单进程可服务多应用。

**FR-6.2 状态作用域**
- 支持 app / user / workspace / session 四级状态作用域。
- session 级状态在会话结束后可选清理；app / user / workspace 级持久。
- **各级作用域有独立的键空间**，不共用一个键：
  - app 级：`{AppName}`
  - user 级：`{AppName, UserID}`
  - workspace 级：`{AppName, UserID, WorkspaceID}`——**独立键空间**，不需要 workspace 进入会话三级键（见 FR-6.0 的载体说明）
  - session 级：`{AppName, UserID, SessionID}`（即 FR-6.1 三级键）
- 这印证了「工作区是会话的属性、而非与 SessionID 平行的维度」：workspace 级状态有自己的寻址路径，无需借助会话键。

**FR-6.3 资源隔离**
- 每个 run 有独立的**执行上下文**（定义见 FR-6.0）与取消信号。
- 支持单 run 超时（MaxRunDuration）。
- 工具并发有每 invocation 的限额。

### FR-10 IM 渠道接入与权限管控（新增）

> **来源**：本节基于对 WeKnora（`E:\aiops\WeKnora`，`internal/im/`）与 HappyClaw（`E:\aiops\happyclaw`，`src/`）的源码调研。HappyClaw 的实现最完整（8 个渠道、12 层权限矩阵），本节以它的抽象为准，取其结构、不取其规模。
>
> **范围**：v1 只做飞书（Feishu/Lark）。但抽象层必须按多渠道路由设计，避免后续接入时重构。

#### FR-10.1 渠道接入与验签

- 每个渠道配置（`IMChannel`）绑定一个 agent，含平台类型、凭据、模式。
- 回调入口必须**先验签再解析**，验签失败返回 403。
- 飞书验签含两层（对齐 WeKnora `feishu/adapter.go:213-231`）：
  - AES-256-CBC 解密（`encrypt` 字段）
  - `Verification Token` 比对（`eventBody.Header.Token != verificationToken`）
- 支持 URL verification challenge（首次配置时飞书的挑战请求）。

**关键设计：渠道配置的管理权限与渠道使用权限分离。**
- **管理渠道**（建/改/删/轮换凭据）：必须管理员门禁（对齐 WeKnora `routes_agent.go:305` 的 `g.Admin()`）
- **使用渠道**（发消息）：走 callback，只验签不验用户身份

#### FR-10.2 主体解析与 namespace 规范化

- 从渠道回调中**实取**用户标识，**不信任调用方传入**。
  - 反面教材：trpc-agent-go 的 `preAuthIdentityMiddleware` 直接从 HTTP header 读 userID（`server_option.go:149`），任何调用方都能声称自己是任何人。
- 飞书的用户标识取 `sender.sender_id.open_id`（对齐 WeKnora `feishu/adapter.go:309, 373`）。
- **不同 Provider 的原生 sender ID namespace 不得混用**（对齐 HappyClaw ACL-MATRIX 第 9 节）。例如 QQ 的 C2C 与 Group 使用不同 ID 空间；owner 比对必须使用渠道适配器传入的规范化 ID。
- 主体表示为 `Principal{Type, ID}`，ID 需带渠道前缀防冲突。
  - 参考 WeKnora `service.go:425` 的四元组：`{tenantID}:{channelID}:{platform}:{userID}`

#### FR-10.3 会话路由：绑定模式 × 路由模式

**这是本节的架构核心。** 会话隔离不是单一开关，而是**两个正交维度**（对齐 HappyClaw `src/types.ts:42-43`）：

```go
// 绑定模式：一条渠道消息如何映射到会话
type BindingMode string
const (
    BindingSingleContext BindingMode = "single_context"  // 整个渠道一个会话
    BindingThreadMap     BindingMode = "thread_map"      // 每个原生话题一个会话
)

// 路由模式：渠道路由到 workspace 的方式
type RoutingMode string
const (
    RoutingSingleSession RoutingMode = "single_session"
    RoutingThreadMap     RoutingMode = "thread_map"
)
```

**话题用虚拟 JID 表达，不重建会话**（对齐 HappyClaw `channel-native-context.ts`）：

```go
// 构造带话题标识的虚拟 JID
func BuildNativeThreadRouteJID(baseJID, contextID, rootMessageID string) string {
    return fmt.Sprintf("%s#thread:%s#root:%s", baseJID, contextID, rootMessageID)
}
```

**飞书话题上下文的归一化**（对齐 `resolveNativeThreadContext`）：

```go
type NativeThreadContext struct {
    ContextID     string  // meta.contextId || threadId || rootId || messageId
    RootMessageID string  // rootId || contextId
    Title         string  // 从首行文本摘要，上限 48 字符
}
```

**关键约束**（对齐 HappyClaw ACL-MATRIX 第 5 节）：
> 原生话题容器使用 `thread_map`，**不能绑定到一个固定 Session 后吞并所有话题**。

每个话题创建**独立的 agent 实例**（对齐 `index.ts:19649` 的 `resolveOrCreateNativeThreadAgent`）：
- 独立 `agent_id`（UUID）
- 独立虚拟 chatJid：`{workspaceJid}#agent:{agentId}`
- 持久化到 `im_context_bindings` 表，主键为 `(source_jid, context_type, context_id)`

**飞书的保守判定**（对齐 `channel-inbound-routing.ts:83-91`）：仅当显式 `nativeContextType === "thread"` 才视为话题。这与 WeKnora 的"顶层消息用 message_id 当 threadID"不同——后者会让每条顶层消息都开新会话，对话连续性差。

#### FR-10.4 触发门禁：响应对象 × 激活方式

**两个正交维度**（对齐 HappyClaw `src/im-audience-policy.ts`）：

```go
// 维度一：谁能触发
type AudienceMode string
const (
    AudienceEveryone  AudienceMode = "everyone"    // 所有允许成员
    AudienceOwnerOnly AudienceMode = "owner_only"  // 仅 owner
)

// 维度二：何时触发
type ActivationMode string
const (
    ActivationAlways        ActivationMode = "always"
    ActivationWhenMentioned ActivationMode = "when_mentioned"
    ActivationDisabled      ActivationMode = "disabled"  // 硬停止
)
```

组合出 6 种策略，两者独立可配。

**门禁判定必须是 fail-closed**（对齐 HappyClaw `feishu-mention-gate.ts` 的血泪教训）：

> 历史 bug：`botOpenId` 为空时旧实现"安全降级 = 默认放行"，导致 `require_mention=true` 在所有群静默失效（**fail-open**）。
> 新行为：`botOpenId` 未知时 **fail-closed（拒绝）**。

判定优先级（对齐 `evaluateMentionGate`）：
1. `activation_mode == disabled` → 拒绝（**硬停止**，即使被 @ 也拒）
2. 非群聊 → 放行
3. `activation_mode == always` → 放行
4. `botOpenId` 未知 → **拒绝**（fail-closed）
5. 未 @ bot → 拒绝
6. `audience_mode == owner_only` 且 sender 非 owner → 拒绝

**@ 判定必须用可信元数据**，不能用文本匹配（对齐 `stripLeadingBotMention` 的注释）：
> 保留 mention 元数据中 bot 的显示 token，避免把用户手写的 `@name` 当作"bot 被提及"的证明。

#### FR-10.5 Owner 模型

- **禁止"第一个发言者自动成为 owner"**（对齐 HappyClaw ACL-MATRIX 第 8 节）。
- 认领路径：
  - 可信的 1:1 私聊可从第一条持久化人类消息学习 owner
  - 群聊用显式命令（如 `/owner_mention`）认领
- 释放与 break-glass：
  - 显式释放命令（`/release_owner`）清除 owner 与 allowlist
  - admin 的 `reset-owner` 作为 owner 离群/换号后的兜底
- **owner 失效必须立即停止响应**（对齐 HappyClaw `owner-gate.ts`）：owner 被禁用/删除后，bot 不能继续响应直到重启。

**注意一处 fail-open**：`owner-gate.ts` 在**无 owner 信息时放行**（`if (!owner) return { allowed: true }`），这是为兼容历史数据。本设计要求**新渠道必须 fail-closed**，无 owner 即拒绝——这是与参考实现的**有意分歧**。

#### FR-10.6 跨面一致性

同一动作在**四个面**必须权限一致（对齐 HappyClaw ACL-MATRIX 第 11 节）：
- HTTP API
- WebSocket
- IM 命令
- MCP（Agent 侧调用）

**admin 不自动绕过资源级所有权**（对齐 ACL-MATRIX 核心原则）：
> admin 不自动绕过工作区所有权。Host 是额外边界：有工作区权限不代表可以执行 Host 操作。

#### FR-10.7 IM 用户的权限降级

- IM 渠道用户**统一降级为最低权限**（对齐 WeKnora `service.go:428` 的 `TenantRoleViewer`）。
- 需要更高权限的操作，引导用户到 Web 端完成。
- 理由：IM 渠道只验签不验用户，无法可靠判定个人角色。

**这一条的代价必须明说**：IM 渠道因此**只能做只读/低危操作**。若业务需要 IM 内写操作，必须增加"用户绑定 + 显式提权"机制（见 FR-10.8）。

#### FR-10.8 用户绑定与提权（可选，v2）

若需要 IM 内高权限操作：
- 用户在 Web 端完成身份绑定（IM 平台 ID ↔ 系统账号）
- 绑定后按系统角色判定权限，而非统一降级
- 绑定关系需可审计、可撤销

#### FR-10.9 审计

- 每次越权拒绝必须留痕：谁（Principal）、在哪（渠道/会话/话题）、想做什么、何时。
- 渠道配置变更（含凭据轮换）必须审计。
- owner 认领/释放/break-glass 必须审计。

#### FR-10.10 防护基线

- **per-user 限流**：按 `{channelID, userID, chatID, threadID}` 滑动窗口（对齐 WeKnora `service.go` 的 `makeUserKey`）。
- **命令豁免限流**：控制类命令（如 `/stop`）必须豁免，保证用户始终能控制 bot。
- **消息去重**：IM 平台会重试，按 message ID 去重（对齐 WeKnora `isDuplicate`）。

## 4. 非功能需求

### NFR-1 并发
- agent loop 支持并发 run，每个 run 独立 goroutine 与 context。
- 事件通过 channel 流式产出，消费者可随时取消。
- 工具执行支持并行安全调用的受控并发池。

### NFR-2 可靠性
- 会话日志写入需保证不丢（append + fsync 策略可配）。
- 崩溃恢复后日志完整，未闭合 turn 有明确修复语义。
- 配置错误 fail-loud，不静默降级。

### NFR-3 性能
- 日志派生（DeriveMessages）应支持增量投影，避免每次全量重放。
- 事件投影需缓存，支持 `stateOf()` 快速读取。
- 长会话的上下文组装不应随事件数线性劣化。

### NFR-4 可扩展性
- 新增能力不修改核心 loop。
- 新增存储后端只需实现存储接口。
- 新增模型 provider 只需实现窄接口。

### NFR-5 可维护性
- 核心接口保持窄（对齐 trpc 的 Model 两方法设计）。
- 显式优于隐式：默认值是显式的 resolve 步骤，不是隐藏的 `?? default`。
- 包边界处的跨域 id 使用品牌类型（branded），不用裸 string。

### NFR-6 平台支持
- Linux / macOS / Windows 三平台。
- **不使用 Go 标准库 `plugin` 包**（不支持 Windows，且无法卸载）。

### NFR-7 版本兼容
- 会话日志格式有版本号，迁移链相邻无缺口。
- 已提交的日志代不可重命名/覆盖/删除。
- 不兼容变更必须显式报错。

### NFR-8 会话串行化（新增）

> **来源**：借鉴 HappyClaw `src/group-queue.ts` 的 per-conversation 串行化机制。这是对 FR-6.3「每个 run 独立执行上下文」的**必要补强**——独立上下文不等于可并发，同一会话的并发 run 会污染同一份 session log。

**NFR-8.1 同一会话不得并发**

- 同一会话的多个 run 必须**串行执行**，不得同时推进同一份 session log。
- 新消息到达时，若该会话已有 active run，只标记待处理并入等待队列，**不启动第二个 run**。
- 对齐 HappyClaw `group-queue.ts:1461` 的 `enqueueMessageCheck`：发现同 serialization key 的 active runner 时只置 `pendingMessages`。

**NFR-8.2 串行化键从会话标识派生，而非直接用会话 ID**

```go
// 串行化键由 resolver 注入，默认回退到会话标识本身
// 对齐 happyclaw/src/group-queue.ts:935-942 的 findActiveRunnerFor
type SerializationKeyResolver func(sessionJID string) string

func DefaultSerializationKeyResolver(jid string) string {
    // 虚拟 JID 需归一到所属工作区，使同工作区的多个会话共享串行化域
    // 对齐 happyclaw/src/index.ts:22189 的三段分支
    switch {
    case isAgentVirtualJID(jid):  // {base}#agent:{agentId}
        return workspaceFolder(jid) + "#" + agentID(jid)
    case isTaskVirtualJID(jid):   // {base}#task:{taskId}
        return workspaceFolder(jid) + "#task:" + taskID(jid)
    default:
        return workspaceFolder(jid)
    }
}
```

**关键洞察**（对齐 `group-queue.ts:935-942`）：匹配依据是**派生键**而非 JID。这样同一 workspace 下不同 JID 的会话会共享同一个串行化域——否则虚拟 JID 会让本该串行的消息并发起来。

**NFR-8.3 容量准入按执行模式分叉**

对齐 `group-queue.ts:944-952` 的设计判据——**资源成本决定是否限流**：

- **进程内执行模式**（无独立资源成本，见 FR-9.1 执行模式定义）：串行化键是**唯一**准入边界，不设全局配额。
  - 理由（源码注释原文）："applying a process-wide slot count here lets warm, idle sessions block unrelated topics"
- **容器/沙箱执行模式**（有真实资源成本，见 FR-9.1）：保留全局并发上限与用户级限额。

**NFR-8.4 防重入双重检查**

- 启动入口检查 active 状态，已 active 直接返回。
- 调度器跳过任何存在 active runner 的候选（**含其自身**）——否则会在同一会话状态上起第二个并发 run，导致重复回复、孤儿进程、计数错乱。
- 对齐 `group-queue.ts:2580` 的 `runForGroup` 与 `:3152` 的 `drainWaiting`。

**NFR-8.5 队列为内存态，消息与游标持久化**

- 队列本身不持久化消息（对齐 `group-queue.ts:215` 的纯内存 `groups` Map）。
- 消息从持久层读取，游标单独落盘（对齐 `index.ts:933` 的 `lastCommittedCursor`）。
- 崩溃恢复靠游标重放，不靠队列状态。

**验收**：同一会话并发投递两条消息，必须串行处理且 session log 无交错。

### NFR-9 运行时控制值与工作区隔离（新增）

> **来源**：借鉴 HappyClaw `docs/RUNTIME-ARCHITECTURE.md` 依赖规则第 4 条与 `src/runtime-config.ts` 的实现。这是一条**安全不变量**，不是性能优化。

**NFR-9.1 控制值来自受信启动环境**

> 原文（`RUNTIME-ARCHITECTURE.md:61`）：*Runtime control values come from the trusted launch environment, not workspace-controlled environment files.*

- 运行时控制值（模型路由、沙箱策略、执行模式、凭据引用）必须来自**进程启动时的受信环境**。
- **不得**从工作区可控的环境文件读取这些值。

**NFR-9.2 工作区不能覆盖受管变量**

对齐 `runtime-config.ts` 的实现——**三处独立检查**（纵深防御）：

```go
// 检查点 1: :647 —— 收集时跳过保留键
if options.SkipReservedClaudeKeys && RESERVED_ENV_KEYS.Has(key) { continue }

// 检查点 2: :2056 —— 构建环境行时再次过滤
if RESERVED_ENV_KEYS.Has(key) || isDangerousEnvKey(key) { continue }

// 检查点 3: :2408 —— 工作区覆盖合并时最终把关
if RESERVED_ENV_KEYS.Has(key) ||
   (merged.BaseURL != "" && THIRD_PARTY_CONFIGURABLE_KEYS.Has(key)) {
    logger.Warn("Skipping managed Claude environment variable in workspace override", key)  // :2413
    continue  // 关键：跳过，不是覆盖
}
```

- 定义**保留键集合**（对齐 `RESERVED_CLAUDE_ENV_KEYS`），工作区提供的同名变量被**跳过**而非生效。
- 第三方可配置键在已设置 BaseURL 时同样受保护。
- **三处检查而非一处**——这是纵深防御的体现：即使某条路径漏检，后续检查点仍会拦截。

**NFR-9.3 环境变量值需清洗防注入**

对齐 `runtime-config.ts:1954` 的 `sanitizeCustomEnvValue`：

- 剥离控制字符，防止环境变量注入。
- 另有独立的 `isDangerousEnvKey`（`:2400`）拦截危险键名。
- 这是**纵深防御**：即使键过滤被绕过，值本身也不能破坏环境文件结构。

**为什么这条重要**：工作区是 agent 可写区域（agent 会读写项目文件）。若控制值可被工作区覆盖，则**agent 能通过写文件提权**——改变自己的沙箱策略、模型路由或凭据引用。这条不变量切断了该路径。

**验收**：在工作区放置含 `RESERVED_ENV_KEYS` 中键名的环境文件，运行时必须跳过并告警，实际生效值仍来自启动环境。

## 5. 关键约束（来自源码调研的硬边界）

以下约束**不是设计选择，是语言与生态的现实**，必须写入设计前提：

| 约束 | 证据 | 影响 |
|---|---|---|
| Go 泛型接口方法不合法 | 实测编译报错 `interface method must have no type parameters` | 类型化事件总线需绕行（每类型一总线 / 代码生成） |
| Go 1.27 支持泛型方法 | 实测 `func (b *Bus) Emit[E any](e E)` 可运行；go.mod 降 1.21 报 `generic method requires go1.27 or later` | 事件总线可用泛型方法，但受上一行限制 |
| Go 标准库 plugin 不可卸载 | 官方文档 `A plugin is only initialized once, and cannot be closed` | 放弃运行时热插拔 |
| Go plugin 不支持 Windows | 官方文档 `only Linux, FreeBSD, and macOS` | 排除该路径 |
| 无 declaration merging | Go 语言特性 | 事件类型声明需显式注册 |
| WASM 是唯一进程内可卸载路径 | wazero 纯 Go 无 CGO，但跨 ABI 只有字节流 | 记为未来演进，不在 v1 |

## 6. 验收标准

### AC-1 日志即真相
- **可观察**：给定一份会话日志，能从中完整重建模型可见的消息序列。
- **可验证**：注入一个"日志与请求不一致"的场景，运行时不变式必须 fail-loud 并给出明确错误。
- **测试**：崩溃恢复测试——写入半截 JSON 后重启，能恢复到最后一个完整事件边界。

### AC-2 可逆 effect
- **可观察**：注册能力后卸载作用域，能力消失且父作用域不受影响。
- **可验证**：注册顺序 A→B→C，卸载顺序必须是 C→B→A。
- **测试**：子作用域卸载后父作用域服务仍可用。

### AC-3 能力 seam
- **可观察**：替换一个 provider（如把本地 FS 换成远程沙箱），依赖它的能力（Bash/PTY/LSP）跟着迁移，无需 fork provider。
- **可验证**：新增一个 provider 不需要修改 Consumer 代码。

### AC-4 多租户隔离
- **可观察**：不同 app / user / session 的数据互不可见。
- **可验证**：并发 run 之间无状态串扰。

### AC-5 生产可观测性
- **可观察**：一次完整 run 能产生完整的 trace（含 chat / tool / agent span）。
- **可验证**：trace 能导出到 OTLP 后端并被正确解析。

### AC-6 扩展不改核心
- **可观察**：新增一个工具 / 一个模型 provider / 一个存储后端，不需要修改 agent loop 代码。
- **可验证**：diff 只涉及新增文件与注册点。

### AC-7 目标不漂移（新增）
- **可观察**：长会话中（≥20 轮）插入与初始目标冲突的局部指令，任务仍按原契约推进，或显式提示冲突。
- **可验证**：上下文压缩后，契约块仍以权威形式存在且状态不回退。
- **测试**：构造"压缩后早期结论与后期证据冲突"的场景，验证契约块优先。

### AC-8 完成有证据（新增）
- **可观察**：模型声称"完成"但未运行验证命令时，门禁返回 RED 而非放行。
- **可验证**：门禁三态与证据状态严格对应（GREEN=自有文件已验证，YELLOW=有外部阻塞，RED=自有失败/未验证）。
- **测试**：构造"未验证编辑后声称完成"场景，门禁必须拦截。

### AC-9 停滞能检测（新增）
- **可观察**：重复调用同一工具 N 次而无状态推进时，运行时发出收敛警告或熔断。
- **可验证**：有真实进度信号（如 todo 推进）时，不误熔断。
- **测试**：构造 doom-loop 场景验证触发，构造正常长任务验证不误报。

### AC-10 分层可逆性（新增）
- **可观察**：编译期装配的核心 hook 不因运行期操作被卸载；运行期注册的扩展可被卸载。
- **可验证**：卸载扩展后核心行为不变；核心 hook 的注册集在会话内稳定。
- **与 FR-2.0 的一致性**：FR-2.0 定义了"核心不可逆 / 扩展可逆"的分层模型，本 AC 验证该分层的实际生效——**注意 FR-2.1 的"返回 Disposer"仅适用于扩展注册层**。

### AC-11 渠道验签 fail-closed（新增）
- **可观察**：伪造签名的回调返回 403；未配置凭据的渠道拒绝服务。
- **可验证**：构造错误签名请求，必须被拒；`botOpenId` 未知时群消息必须被拒（不得放行）。

### AC-12 话题隔离（新增）
- **可观察**：飞书群内不同话题的消息进入**不同会话**，上下文互不污染。
- **可验证**：在同一群的两个话题分别提问，agent 不应把 A 话题的上下文带入 B 话题。
- **反模式检查**：不得出现"一个固定 Session 吞并所有话题"。

### AC-13 用户身份不可伪造（新增）
- **可观察**：渠道回调中的用户身份来自平台元数据，不接受调用方参数。
- **可验证**：构造带伪造 userID 字段的请求，实际主体仍取自平台 `open_id`。

### AC-14 触发门禁（新增）
- **可观察**：`owner_only` 模式下非 owner 消息不触发 agent；`when_mentioned` 模式下未 @ 不触发。
- **可验证**：两个维度独立组合，6 种策略各自行为正确。

### AC-15 跨面权限一致（新增）
- **可观察**：同一动作经 HTTP / WS / IM / MCP 四个面，权限判定一致。
- **可验证**：对同一资源，非 owner 在四个面均被拒绝；admin 不绕过资源所有权。

### AC-16 会话串行化（新增）
- **可观察**：同一会话并发投递多条消息，处理是串行的，session log 无事件交错。
- **可验证**：并发压测同一会话，断言任意时刻该会话至多一个 active run。
- **反模式检查**：不得出现同一会话两个 run 同时写 session log。

### AC-17 控制值不可被工作区覆盖（新增）
- **可观察**：工作区放置含保留键的环境文件，运行时跳过并告警。
- **可验证**：注入 `RESERVED_ENV_KEYS` 中的键名，实际生效值仍来自启动环境。
- **安全断言**：agent 通过写工作区文件**不能**改变自己的沙箱策略、模型路由或凭据引用。

## 7. 分期规划建议

**Phase 1（核心内核）**
- 会话日志（append-only + 派生 + 崩溃恢复）
- 可逆 effect 注册机制
- 能力 seam 骨架
- 标准 agent loop + 事件扩展点
- 内存 + SQLite 后端

**Phase 2（生产化）**
- 多租户隔离
- **NFR-8 会话串行化**（新增，P0）
- **NFR-9 运行时控制值与工作区隔离**（新增，P0）
- OpenTelemetry 可观测性
- PostgreSQL 后端
- 工具执行管线 + 并发控制
- 多 provider 支持

> **NFR-8/NFR-9 为何放 Phase 2 而非 Phase 4**：两者都不是渠道特性，而是**内核级约束**。
> - NFR-8 依赖 Phase 1 的 session log——串行化正是为了防止并发污染日志，两者必须配套。
> - NFR-9 依赖 **FR-9.1 沙箱设计**——控制值清单要等执行模式（进程内/容器）定稿才能确定。
>   **注意**：FR-9.1 排在 Phase 3，而 NFR-9 排在 Phase 2，存在顺序倒置。
>   **处理**：Phase 2 先实现 NFR-9 的**保留键保护**（不依赖执行模式），执行模式相关的控制值清单留到 Phase 3 补齐。
>
> 若推迟到 Phase 4 才补，Phase 2 的并发实现会先建立错误的假设（认为同会话可并发），届时需返工。

**Phase 3（生态）**
- MCP 集成
- 多 agent 编排（chain/parallel/cycle）
- 沙箱与权限策略
- 摘要与上下文压缩
- 更多存储后端

**Phase 4（渠道接入，新增）**
- FR-10.1 渠道接入与验签（飞书优先）
- FR-10.2 主体解析与 namespace 规范化
- FR-10.3 会话路由（绑定模式 × 路由模式，含话题虚拟 JID）
- FR-10.4 触发门禁（响应对象 × 激活方式，fail-closed）
- FR-10.5 Owner 模型（显式认领 + break-glass）
- FR-10.6 跨面一致性（**须在 Phase 2 预留接口**，否则 Phase 4 触发重构）
- FR-10.7 IM 用户权限降级
- FR-10.9 审计
- FR-10.10 防护基线（限流/去重/命令豁免）
- **验证命令**：`go test ./channel/... -race && go test -tags=integration ./channel/feishu/...`

> **Phase 4 依赖 Phase 2 的多租户隔离**——渠道身份最终要落到 `{AppName, UserID, SessionID}` 键上。
>
> **Phase 4 的范围约束**：只做飞书，但抽象层按多渠道路由设计。FR-10.6 跨面一致性要求 HTTP/WS/IM/MCP 四面的权限判定统一——这一条应在 Phase 2 就预留接口，否则 Phase 4 会触发重构。
>
> **Phase 5（可选，v2）**：FR-10.8 用户绑定与提权（若业务需要 IM 内写操作）。

### B.1 按执行上下文收紧写权限

**机制**（对齐 `docs/workspace-memory-v2.md:101-110`）：

| 执行上下文 | 读取 | 写入 |
|---|---|---|
| 顶层交互式 Main/Runtime Session | 允许 | 按 Workspace ACL |
| Scheduled Run（group/isolated） | 允许 | **拒绝** |
| SDK Task Sub-Agent | 允许 | **拒绝** |

**核心洞察**：把 **LLM 视为不可信主体**。理由（对齐 `docs/ACL-MATRIX.md` 第 10 节）：

> admin Home Agent 是**会接触不可信内容的 LLM**，而任务 `prompt` 会被按计划重放、以 Bot 身份在目标会话发言、并计费到目标工作区。

**为什么未纳入**：需要"执行上下文"成为一等概念并沿调用链传播。本文档目前没有这个抽象，引入它意味着 Runner 要携带上下文类型并在所有写入路径校验。

**代价**：每个写操作都要判定上下文类型；上下文丢失时需 fail-closed。

### B.2 容量准入按执行模式分叉

> 注：NFR-8.3 已吸收其**判据**（资源成本决定是否限流），此处记录完整形态。

**机制**（对齐 `group-queue.ts:944-952`）：Host 模式不做全局配额（串行化键是唯一准入边界），Container 模式保留 `maxConcurrentContainers` 与用户级限额。

**为什么未完全纳入**：本文档尚未定义"进程内 / 容器"两种执行模式。等 FR-9.1 沙箱设计落地后，此条可直接套用。

### B.3 性能预算 + 测试锁住

4 条预算，**每条都有对应测试**：

### B.4 Workspace Memory 一致性模型

**机制**（对齐 `docs/workspace-memory-v2.md:69-87`）：

- **四层数据分离**：平台身份 / Owner Profile / Session 历史 / Workspace Memory
- **CAS 防丢失更新**：`expectedRevision` + 409 `revision_conflict`，冲突时客户端**保留草稿不自动重发**
- **忘记用 tombstone**：审计历史保留，活跃列表不返回
- **幂等键**：重放返回 `replayed: true`，同 key 不同请求返回 `idempotency_conflict`
- **条目分类强制四选一**：`fact` / `decision` / `lesson` / `open_loop`

**为什么未纳入**：本文档 FR-8 持久化只定义了会话与事件，未定义"长期知识层"。若需要记忆层，此模型成熟可直接参考。

**代价**：CAS + revision 显著增加写入路径复杂度；对简单场景是过度设计。

### B.5 模块边界与依赖规则

**机制**（对齐 `docs/RUNTIME-ARCHITECTURE.md` 的 Dependency rules 段）：

1. Provider 连接器可依赖渠道/领域契约，**绝不能依赖 Web 网关**或其他 provider 实现
2. 路由可调用应用/数据库服务与注入的投影，但**不得反向 import** 主网关
3. 可选 provider SDK 必须经惰性注册表访问
4. **运行时控制值来自受信启动环境，不来自工作区可控的环境文件**（已纳入 NFR-9）
5. 生产容器执行版本化构建产物，运行时不编译
6. 新增共享消息应使用**类型化契约**，而非给通用 payload 加不相关的可选字段

**为什么未纳入**：这是**文档级资产**，不依赖实现。可在 Phase 1 开工时直接采纳为项目约定。

### B.6 其他可靠性机制（仅记录，未评估）

调研中发现的以下机制，**未做完整评估**，仅记录供后续参考：

- **`stuck-runner`**：检测并重启卡死 runner，含 CPU 探针**不跨运行时边界**的设计（容器直接返回 unavailable，避免把 docker CLI PID 误当容器负载）
- **`leftover-direct-mount-*`**：修复迁移后的残留挂载，默认 dry-run，alias 冲突时拒绝自动修复
- **`delivery-cursor`**：投递游标用**精确成员集合**判定而非范围（避免同批早成员被误判为 gap）
- **投递结算显式 ACK**：`false` 视为失败而非确认，区分 success/partial_failed/failed/uncertain，仅 failed 进入重试
- **不确定投递不自动重发**：`uncertain` 行需人工放行
- **任务定义不可变快照**：路由只用 `definition_snapshot` 不用 live 定义

**未评估原因**：这些是**运行时可靠性细节**，需要先有 Runner/调度器的实现才能判断是否需要。等对应模块开工时再回看。
