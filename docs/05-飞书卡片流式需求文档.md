## 1. 问题陈述

### 1.1 现状

飞书回复是**纯文本消息**。实测代码：

```go
// internal/channel/feishu/send.go:109（create）
MsgType(larkim.MsgTypeText).
Content(content).       // content = {"text":"..."}

// send.go:136（update）
MsgType(larkim.MsgTypeText).
```

后果：**Markdown 无法渲染**。飞书纯文本消息不解析 Markdown，`**粗体**`、`- 列表项`、` ```代码块``` ` 全部退化为裸字符。

### 1.2 实际影响（真实场景）

Infraverse MCP 查询返回结构化结果，在飞书里显示为：

```
反查结果：
- 集群: sit-dce5-data-cluster
- 命名空间: digital-e360-data-sit
- Pod: redis-cluster-e360-sit-leader-0
- 节点: wcn-gduva-mwdsit8
- 状态: Running
- IP: 10.82.130.65
```

这些 `- ` 是**模型自己写的 Markdown 列表语法**，本该渲染成项目符号列表，实际显示为连字符开头的纯文本。更长的回答（含代码块、表格）退化更严重。

### 1.3 另一个缺失：无流式观感

当前是"占位消息 → 一次性替换"（`pipeline.go:184` 发占位，`:210` 更新为完整回答）。用户看到的是一次**突然出现**的完整回答，中间过程只有「思考中…」。

设计文档 §4.4.1（`docs/03-原型设计文档.md:498`）记载这是**有意的简化取舍**：

> 原型用**简化版流式**——先发一条占位文本消息，收到完整回答后用飞书的**更新消息 API** 替换。代价是看不到逐 token 打字效果，收益是省掉 CardKit 的完整状态机。**若验收线 4 要求卡片流式，再补该接口**。

本需求即兑现该演进。

## 2. 需求目标

### 2.1 功能性目标

| 编号 | 目标 | 优先级 |
|---|---|---|
| FR-1 | 飞书回复以**卡片**承载，Markdown 正确渲染 | 必须 |
| FR-2 | 生成过程中卡片内容**逐步增长**（打字机效果） | 必须 |
| FR-3 | 流式协议合规（`streaming_mode` 开关 + `sequence` 递增） | 必须 |
| FR-4 | CardKit 失败时**降级到纯文本**，用户不收到空白回复 | 必须 |
| FR-5 | 长回答的行为明确（截断或分段，不静默丢失） | 必须 |
| FR-6 | 出站接口支持消息形态选择（文本/卡片），不破坏既有调用 | 必须 |

### 2.2 非目标（明确不做）

| 编号 | 不做的事 | 理由 |
|---|---|---|
| NG-1 | 卡片交互回调（按钮点击、表单提交） | 属会话治理范畴，与本次渲染目标正交 |
| NG-2 | 多卡片编排（一个回答拆成多张卡） | 复杂度高，收益未验证 |
| NG-3 | 卡片模板管理（可视化编辑/复用） | 原型阶段不需要 |
| NG-4 | 富媒体（图片、文件上传进卡片） | 与本次目标无关 |
| NG-5 | 保留纯文本模式作为可选项 | 卡片失败时自动降级即可，无需配置开关 |

## 3. 技术前提（已调研确认）

### 3.1 SDK 能力

`oapi-sdk-go v3.9.7` 的 `service/cardkit/v1` 提供完整流式能力（实测枚举）：

| API | 用途 |
|---|---|
| `card.Create` | 创建卡片实体 → 返回 `card_id` |
| `card.Settings` | 开关 `streaming_mode`（带 `sequence`） |
| `cardElement.Content` | **流式更新元素文本**（打字机效果的关键） |
| `card.BatchUpdate` | 批量更新元素 |
| `card.Update` | 整体替换卡片 |
| `cardElement.Patch` / `Delete` | 元素级增删改 |

### 3.2 流式协议（SDK 原文注释为准）

`SettingsCardReqBody.Sequence`（`model.go:2267`）：

> 卡片处于流式更新模式时，进行卡片操作的顺序序号，用于保证多次更新的时序性。值为正整数，一次流式状态的多次更新操作（**streaming_mode 一次从 true 到 false 期间**）需要保证 sequence 递增，否则将报错。推荐使用时间戳。

`ContentCardElementReqBody.Sequence`（`model.go:2615`）：

> 顺序序号，用于保证更新文本内容的时序性。在卡片的单次 streaming 模式周期中（streaming 状态从开始到停止），该值需为递增的正整数，否则将报错。

**协议形态**：

```
Settings(streaming_mode=true, sequence=N)
  → Content(sequence=N+1)
  → Content(sequence=N+2)
  → ...
  → Settings(streaming_mode=false, sequence=M)
```

### 3.3 消息类型

`MsgTypeInteractive = "interactive"`（`ext_model.go:658`）——卡片消息的 `msg_type`。

## 4. 现有架构的约束（实测）

### 4.1 出站接口无消息类型位

```go
// internal/channel/outbound.go
SendMessage(ctx context.Context, to, text string, opts SendOptions) (string, error)
//                                  ^^^^^^^^^^ 纯文本，无类型位
```

`SendOptions` 只有两个字段：

```go
type SendOptions struct {
    ReceiveIDType ReceiveIDType  // open_id / chat_id
    MessageID     string         // 空=新建，非空=更新
}
```

**这意味着**：设计文档 `:498` 声称的"接口位已预留"**不成立**——没有任何为卡片预留的结构。接口需真实设计。

### 4.2 需要迁移的调用点（实测计数）

| 类别 | 数量 | 文件 |
|---|---|---|
| 生产调用点 | **1** | `internal/server/pipeline.go:210` |
| 测试夹具/调用 | **8 个文件** | `server/e2e_test.go`、`principal_e2e_test.go`、`log_privacy_e2e_test.go`、`feishu/send_test.go` 等 |

生产调用点少（1 处）是**有利条件**：接口改动的实际波及面集中在测试。

### 4.3 流式管道已存在（重要发现）

`internal/chat/execute.go:240` 的 `runOneTurn` **已有 `emit func(string)` 回调**：

```go
func runOneTurn(ctx context.Context, r runner.Runner, opts Options, sessionID, input string, emit func(string)) error
```

但 `Executor.Execute`（`:111`）把它用来**拼接**而非逐块外传：

```go
var sb strings.Builder
if err := runOneTurn(ctx, e.asm.runner, e.asm.opts, sessionID, text, func(chunk string) {
    sb.WriteString(chunk)     // ← 只拼接，不通知调用方
}); err != nil {
    return "", err
}
return sb.String(), nil
```

**结论**：流式的**底层管道已就绪**，缺的是"把 chunk 外传给管道层"。这显著降低了 FR-2 的实现成本。

## 5. 验收标准

| AC | 标准 | 验证方式 |
|---|---|---|
| AC-1 | 飞书收到 `msg_type=interactive` 的消息 | 假端点断言请求体 |
| AC-2 | 生成过程中至少 2 次可见的内容更新 | 假端点记录调用序列 |
| AC-3 | Markdown 正确渲染（列表/代码块/粗体） | 卡片 JSON 结构断言 + 真实飞书目视 |
| AC-4 | 流式协议合规（sequence 递增、streaming_mode 正确开关） | 假端点断言序列 |
| AC-5 | CardKit 报错时降级纯文本，用户收到完整回答 | 注入失败 + 断言降级调用 |
| AC-6 | 长回答不静默丢失 | 超长输入 → 断言行为明确（截断有提示或分段） |
| AC-7 | 既有 9 包测试全绿（接口迁移无回归） | `go test ./...` |

## 6. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| CardKit API 与文档不符（无真实环境验证） | 实现可能需返工 | 假端点测协议形态；真实飞书验证作为交付前置 |
| `sequence` 语义理解偏差（如时钟回拨） | 流式更新被平台拒绝 | 用单调递增计数器而非时间戳；失败时降级 |
| 接口改动波及 8 个测试文件 | 迁移成本 | 生产调用点仅 1 处；接口设计优先保持向后兼容 |
| 卡片元素内容长度限制未知 | 长回答截断 | 实现前实测限制；超限行为写入 AC-6 |
| 降级路径未测 | CardKit 故障时用户收到空白 | AC-5 强制覆盖 + 反向验证 |
