Issue #0005 — 飞书入站：验签 + 解密 + 解析 — 2026-09-23

Design Decisions

Decision 未知 chat_type 一律归为 group

歧义点：设计文档只列出 direct | group 两个取值，未规定平台返回未知值时如何归一化。

选择：normalizeChatType 仅在平台值为 "p2p" 时返回 ChatDirect，其余（含空串）一律返回 ChatGroup。

理由：群聊要过 @ 门禁，私聊直接放行。把未知值当 direct 会绕过门禁——正是 docs/03-原型设计文档.md:576 记录的那类静默失效（happyclaw 旧版 botOpenId 为空时"安全降级=放行"导致 require_mention 在群内静默失效）。归一化方向必须朝 fail-closed。

Decision 渠道凭据独立成 CredentialKeys 集合

歧义点：设计文档 §4.6 只列出六个控制值键（MODEL_ROUTE 等），完全未提渠道凭据是否受同等保护、该放进哪个集合。

选择：新增 CredentialKeys（FEISHU_VERIFICATION_TOKEN / FEISHU_ENCRYPT_KEY / FEISHU_APP_ID / FEISHU_APP_SECRET），与 ReservedKeys 分列，在 isReserved 检查点合并。

理由：两者威胁模型不同——控制值被覆盖是提权（改沙箱策略、模型路由），凭据被覆盖是凭据劫持（把验签口令换成攻击者已知值，伪造事件即可通过验签，渠道边界当场失效）。但防护动作相同（工作区同名键一律跳过），故分列集合、合并检查点：既保留分类语义便于审计，又只有单一过滤点。

Decision 引入 400 区分"已验签但畸形"与"认证失败"

歧义点：issue 只规定了 403（验签失败）。未规定"验签通过但事件体畸形"该回什么。

选择：状态码映射为 405（非 POST）/ 403（凭据未配置、验签失败、解密失败）/ 400（已通过验签但消息事件缺必需字段）/ 200（通过）/ 500（下游失败，让飞书重试）。

理由：验签已通过的畸形请求不是认证失败，混用 403 会让运维在排查时误判为凭据问题。500 的选择也有语义：下游不可用时不能让飞书认为投递成功，否则平台不再重试、消息永久丢失。

Decision 文本提取按"能否解析出 text 字段"判定，而非按 message_type

歧义点：未规定 message_type 字段缺失时的行为。飞书事件体的 content 是一个 JSON 字符串（如 {"text":"hello"}），非纯文本。

选择：extractText 直接尝试解析 {"text":...}，能解出就用，解不出返回空串。

理由：初版按 message_type == "text" 把关，实测 TestHandler_LogsParsedFields 失败——日志里 text=""，用户输入被丢弃。而两种判定对非文本消息（image 的 {"image_key":...}、post 的 {"title":...,"content":[[...]]}）结果一致（都是空串），所以按内容判定不牺牲任何安全性，却不会因信封字段缺失而丢失正文。这是测试驱动暴露的真实缺陷，不是构造问题。

Deviations

Deviation 未定义连接层 Channel 接口

规范怎么说：docs/03-原型设计文档.md:248（§3.3 目录结构）把 internal/channel/channel.go（连接层 Channel 接口）列为渠道层的第一个文件。

实际实现：只定义 internal/channel/inbound.go（入站层 InboundSource），不定义 Channel。

为什么：issue #5 明确"只做 webhook 入站；出站与端到端闭环见后续 Issue"，且 6 条 AC 全部落在 InboundSource 三方法面上。Channel 需要 SendMessage（出站，#9 范围）与长连接（#9 范围），现在定义会产生三个永不调用的空方法——正是设计文档 §4.4.1 反对的单接口形态。代价：目录结构与 §3.3 暂不一致；收益：零 stub、零未验证代码面。#9 实现连接层时再定义，届时 var _ Channel = (*feishu.Channel)(nil) 编译期断言才有真实对象可锁。

Deviation 凭据未配置时拒绝 URL 挑战请求

规范怎么说：设计文档 §4.4.2 引用的参照实现 WeKnora internal/im/feishu/adapter.go:238-283，其 HandleURLVerification 只做解密与 challenge 提取，不校验凭据——未配置 token 的部署仍会应答挑战。

实际实现：凭据未配置时，handler 在挑战判定之前就返回 403，连挑战请求一并拒绝。

为什么：issue #5 的 AC 原文是"未配置 verification token 时，端点拒绝所有回调（fail-closed），不是放行"。把挑战请求排除在该约束外，等于承认"凭据缺失时端点仍对外服务"。代价必须明说：未配置凭据的部署无法完成飞书首次 URL 校验，会看到 403 而非 challenge 回显。这是期望行为——配置凭据是启用端点的前置条件，不是可选调优项。

Deviation 扩展了 §4.6 的保护键集语义

规范怎么说：设计文档 §4.6 定义"保留键"= 六个运行时控制值键，其语义是"agent 可写工作区不得覆盖的控制面"。

实际实现：ReservedKeys 保持六键不变，另立 CredentialKeys 四键；过滤函数从"仅查 ReservedKeys"改为"查两者并集"。

为什么：严格说这是规范未覆盖而非违背，但它确实改变了 MergeWorkspaceEnv 的行为边界——原先"保留键"等价于控制值，现在受保护面含凭据。如实记录，因为 §4.6 末尾关于"v1.4 NFR-9.2 要求三处纵深防御、原型降级为一处"的说明只针对控制值，未涵盖凭据路径。

Tradeoffs

Tradeoff token 比对 vs X-Lark-Signature 签名校验

备选：① 仅比对 header.token（参照实现路径）；② 补 X-Lark-Signature 签名校验（timestamp + nonce + encryptKey + body 拼接）。

取舍：选 ①。设计文档 §4.4.2 已标注"签名算法的精确拼接顺序本会话未逐字核实"（官方文档页为 SPA 无法抓取正文），采用 token 路径规避该不确定性。

代价：token 随事件体传输，强度依赖 TLS 与 token 保密，弱于基于密钥的签名。若后续核实了签名算法，应在 VerifyCallback 补第三层校验——接口位无需变动。

Tradeoff 常量时间比对 vs 普通 ==

备选：① ev.Header.Token == s.cfg.VerificationToken；② subtle.ConstantTimeCompare。

取舍：选 ②。代价是可读性略降（需处理长度不等时的短路语义）；收益是不逐字节泄露前缀匹配长度，消除时序侧信道。对本地验签路径属低成本高收益。

Tradeoff 凭据未配置时"启动并拒绝" vs "启动失败退出"

备选：① serve 发现无 FEISHU_VERIFICATION_TOKEN 即报错退出；② 打印警告后仍启动，由端点拒绝一切请求。

取舍：选 ②。收益：运维能看到"监听 :8080，webhook 路径 /webhook/feishu"与明确的原因说明，而不是一个静默退出的进程。代价：服务"起来了但不工作"，依赖运维阅读警告；若选 ①，容器编排会因反复重启掩盖真实原因。

Tradeoff 12 文件单提交 vs 按内聚性门禁拆分

备选：① 按门禁建议拆成多个提交；② 用 force=true 覆盖门禁，单提交。

取舍：选 ②。理由：internal/channel/feishu/config.go 的一致性测试 TestCredentialEnvKeysMatchConfigGuard 依赖 internal/config/guard.go 的 CredentialKeys；拆开会让中间提交处于编译失败或测试红状态。收益：每个提交都是绿的。代价：单提交较大（2051 行），审查面宽。

Tradeoff 单独提交 main.go vs 等待并发会话

备选：① 不提交 main.go，留给 #2 会话；② 单独提交并在 message 中如实标注。

取舍：选 ②。理由：main.go 的未提交 diff 中，#2 的 runChat 接线与本次的 runServe 接线共享同一个 import 块（internal/chat 与 internal/channel/feishu 同块），git 无法按 hunk 拆分——单独提交任一侧都会因 "imported and not used" 编译失败。代价：该提交（53f30a2）含非本 issue 代码，归属上不完全干净。已确认 f88f597 未包含 main.go，故不存在覆盖 #2 在途改动的风险。
